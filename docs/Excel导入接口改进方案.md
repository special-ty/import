# 信息系统 Excel 导入接口改进方案

- 编写日期：2026-11-02
- 适用项目：本仓库（`import`）
- 对照项目：`dataCenter_backend`（独立仓库，本地位置不作约定）
- 目标接口：`POST /system/manage/importSystem`
- 文档状态：方案汇总，后续分阶段实施；本文件不代表相关代码已经完成。
- 实施原则：全部改进纳入规划，按阶段落实；未确认的业务规则和技术选择在对应阶段编码前与用户确认。

## 1. 背景与目标

本项目是原项目导入接口的最小运行实现，保留 Controller → Service → EasyExcel Listener → Mapper 的调用结构，使用 MySQL、固定操作用户及数据库字典查询，未引入原项目的认证、Redis 等基础设施。

当前实现先校验整份文件，再批量新增。用户明确希望改为：

> 合法行可以成功插入；无法插入的行记录失败原因到数据库，供前端后续展示，不因普通行错误导致整份导入失败。

本方案同时覆盖重构、性能、审计、数据准确性、并发一致性、幂等、可观测性及大文件演进。

### 1.1 已确认需求

1. 支持部分成功：行级校验或插入失败不应影响其他合法行。
2. 失败原因持久化，后续可以提供给前端展示。
3. 将此前讨论的全部改进整理到本文档，分阶段实现，不要求一次完成。
4. 当前仅编写文档，不开展代码改造，不运行测试、不连接数据库或执行初始化 SQL。

### 1.2 沿用的业务基线

以下沿用当前只新增导入规则，不因优化而擅自扩展：

- 导入不更新、不覆盖已有系统。
- 库内查重当前范围为全局 `system_name + status='1'`；仅软删除的同名记录不阻止新增。
- 表格包含七列：信息系统名称、信息系统状态、部署方式、当前所属单位、实施单位、接入网络类型、功能描述。
- 单位和字典显示值需要解析为合法的组织 id 和字典 code。
- 最小项目保留 MySQL，不为实现本方案强制引入 Redis、消息队列或完整认证系统。

如需改变唯一范围、模板字段或引入原项目权限体系，必须另外确认。

## 3. 当前问题清单

1. 转换阶段逐行 `catch` 后仅打印异常，可能少插数据但仍返回成功。
2. 字典只校验非空，未严格校验合法值；查不到 code 时可能将 null 写入。
3. 单位先查数量、后按名称查 id，重复查询且同名多机构时可能任取一条。
4. 逐行查重、单位校验、字典转换及单位解析产生大量查询，本项目每条完整合法行约 8 次读取查询，不含写入。
5. 当前批内集合与 MySQL 排序规则可能具有不同的名称等价语义。
6. 仅靠先查询再插入无法保证并发名称唯一，缺少数据库兜底。
7. Listener 同时承担解析、业务校验、转换和保存，依赖通过静态容器工具隐式获取。
8. 缺少字段长度校验、完整文件边界校验及明确的空模板反馈。
9. 行号提示直接使用零基索引，与 Excel 实际行号相差一。
10. 缺少批次、失败明细、结果核对和安全重试机制。
11. 无法从现有日志准确区分解析、参考数据加载、校验及写入耗时。
12. 虽然 EasyExcel 逐行解析，但监听器保存全部合法行，整体不是 O(1) 内存。

## 4. 目标行为

### 4.1 逐行导入流程

```text
接收文件与操作上下文
  → 创建批次
  → 文件、格式、模板检查
  → 准备参考数据或按需加载缓存
  → EasyExcel 逐行解析
      → 保留 Excel 实际行号及必要原始值
      → 校验、名称规范化及单位/字典解析
      → 合法：独立事务新增并记录成功处理结果
      → 普通行失败：独立记录失败明细，继续下一行
      → 致命错误：停止后续处理，记录中断状态
  → 核对处理结果，更新批次状态
  → 返回批次号及统计，或由异步查询获取结果
```

### 4.2 错误分类

| 类别 | 示例 | 处理原则 |
|---|---|---|
| 行解析错误 | 可准确定位的单元格类型转换错误 | 能安全继续读取时记录该行失败，避免重复统计同一行 |
| 行校验错误 | 必填、长度、字典无效、单位不存在或歧义 | 记录全部可收集的行内问题，继续 |
| 行业务冲突 | 库内重名、按确认规则判定的批内重名 | 记录失败，不覆盖已有系统 |
| 可识别的单行数据库约束冲突 | 确认由系统有效名称唯一约束触发的冲突 | 当前行回滚，映射为稳定业务错误，记录后继续 |
| 文件级错误 | 表头不匹配、文件损坏、超出限制 | 停止；如已有提交，结果须表达中断且部分数据已成功 |
| 系统级错误 | 数据库不可用、失败明细无法持久化、未知写入异常 | 不得无限重试或静默继续；停止并记录/恢复中断状态 |

不能将所有 `DuplicateKeyException` 一概解释为系统名称重复，必须识别实际约束；未知完整性异常应保留内部诊断信息并安全处理。

### 4.3 结果状态

建议使用以下内部状态，具体接口枚举命名按 C07 确认：

- `PROCESSING`：处理中。
- `SUCCESS`：处理完成，至少一行成功且没有失败行。
- `PARTIAL_SUCCESS`：处理完成，既有成功行也有失败行。
- `FAILED`：处理完成但全部数据行失败，或在任何业务写入前发生不可继续的错误；通过错误类型区分。
- `INTERRUPTED`：未完整处理文件，可能已经有成功提交。
- `NO_DATA`：只有表头等情况，没有可处理数据，避免笼统返回导入成功。

异步阶段可增加 `PENDING` 等状态。所有终态必须有明确结束原因，不用成功数推测任务是否完整结束。

## 5. 数据准确性与并发约束

### 5.1 校验及转换

- 七个业务字段必填，按列名返回可理解的错误。
- 系统名称和功能描述按数据库限制校验长度，并明确字符/字节及异常字符处理规则。
- 字典校验有效状态、显示值匹配及唯一性；未知值或多码歧义不得任意转 null 或取第一条。
- 单位一次解析为“无匹配/唯一匹配/多匹配”，唯一匹配时复用 id，不再先查存在再查 id。
- 生产适配需要校验操作人对目标机构的权限；最小项目固定用户不能被宣称为已完成权限控制。
- 业务值规范化与保留原值分开，避免清洗过程损坏业务含义。
- 表头按 `@ExcelProperty.index` 排列，不依赖反射字段顺序；列外内容和模板版本策略需明确。
- 用户可见行号使用 Excel 实际行号，保存来源行信息以支持转换与写入错误定位。

### 5.2 唯一性

应用层检查用于友好反馈，数据库约束保证并发正确性，两者不可相互替代。

MySQL 方案可使用“有效名称生成列 + 唯一索引”：有效状态映射到符合确认规则的名称键，其他状态映射到 NULL，允许保留多条软删除历史。

注意事项：

- 不直接使用 `UNIQUE(system_name, status)`，避免限制同名软删除历史。
- 唯一范围沿用全局有效名称，除非另行确认按组织分组。
- 应用规范化与数据库比较/排序规则必须一致，不能假设 Java `HashSet` 与 MySQL 默认比较相同。
- 加约束前检查历史重复、空值与长度，制定修复及回退步骤，不自动删除或合并历史数据。
- 不将普通事务或分布式锁当作数据库唯一约束的替代。

### 5.3 数据库基础约束

按业务实际逐步评估必填字段 NOT NULL、引用完整性与审计字段约束。添加外键或其他约束需兼顾原项目软删除和实际部署数据库，不直接照搬 MySQL 方案到 GaussDB。

## 6. 重构与事务设计

### 6.1 职责划分

| 组件 | 职责 |
|---|---|
| Controller | 接收文件、读取上下文、返回约定结果 |
| ImportApplicationService | 编排批次、解析、处理策略及终态 |
| Excel Listener / Reader | 读取表头、行号和输入，转交行处理，不直接承包业务 |
| ReferenceDataResolver | 加载并解析单位、字典、已有名称等参考数据 |
| RowValidator / Assembler | 校验和转换，产出待插入对象或结构化错误 |
| RowImportService | 独立事务写入业务记录及成功处理证据 |
| ImportAuditService | 批次、失败结果、统计与恢复协调 |

不为每个简单校验强制创建独立类；以职责清晰、容易测试为目标。Listener 可每次请求新建，依赖通过构造方法传递，不继续使用静态容器查找隐藏依赖。

### 6.2 事务边界

- 不给整份文件套一个写事务，不持有覆盖整个解析周期的数据库事务。
- 行写入通过独立 Spring Bean 的代理方法执行，可采用 `REQUIRES_NEW` 明确隔离。
- 不能通过同类内部调用假定 `@Transactional` 已生效。
- 校验及转换尽可能在写事务外完成；行插入失败先回滚，再由调用方记录失败。
- 失败明细独立提交，不能写在刚失败的事务里。
- 业务写入和该行成功处理证据在同一事务提交，保证结果可以恢复、核对。
- 批次统计是可重建汇总，不将单纯内存计数当作唯一事实来源。
- 在提交结果未知的情况下，禁止无条件再次插入或直接认定失败；应依靠行处理标识核对结果。

## 7. 审计数据模型

下列为逻辑模型，字段类型、枚举、索引及迁移脚本在实施时细化。

### 7.1 批次表 `dc_system_import_batch`

建议字段：

- `id`、文件名、文件大小、文件摘要、模板版本。
- 操作人、所属组织、请求标识；原项目适配时使用真实认证上下文。
- 执行模式、状态、开始/结束时间、最近进度更新时间。
- 已处理行数、成功行数、失败行数；实际总行数未知时保持未知，不拿已处理数冒充总数。
- 文件级/系统级错误码与安全摘要。
- 幂等键及其主体范围（启用幂等时）。

### 7.2 行处理结果表 `dc_system_import_row_result`

建议统一记录成功及失败行，避免只记录失败而无法可靠核对成功结果；失败行查询可直接从此表筛选。

建议字段：

- `id`、`batch_id`、工作表标识（如支持多 sheet）、Excel 行号。
- 处理状态、系统名称/规范化键、成功关联的业务主键。
- 失败阶段、稳定错误码、前端可见原因、字段级错误列表。
- 必要的原始行数据、处理时间。

唯一键建议为单 sheet 时 `(batch_id, row_number)`；多 sheet 时纳入 sheet 标识。

这是前面“失败明细表”方案的可靠性增强版本：逻辑上仍满足失败原因入表供前端查询，同时支持成功事务核对与中断恢复。若希望物理拆为成功结果表和失败表，应在审计阶段确认；不能省掉成功处理证据却宣称具备精确恢复能力。

### 7.3 审计一致性和隐私

- 成功业务记录及成功行结果原子提交。
- 普通行失败独立保存；写失败结果本身失败属于致命错误，不伪造正常完成。
- 进程崩溃后由持久化行结果重建统计，识别长期处理中批次。
- 失败信息不直接暴露 SQL、连接信息、堆栈及内部服务详情；内部日志用批次号和行号关联。
- 文件与原始行内容受权限、脱敏、保留期限约束，清理操作需要有范围和审计。

## 8. 接口与前端需求

接口路径和返回枚举待 C07 确认，建议保持原上传入口并增加：

1. 上传接口：返回批次号、处理状态、成功/失败/已处理数量；同步时返回终态，异步时返回已受理状态。
2. 批次详情：查询状态、数量、异常摘要和处理时间。
3. 失败明细分页：按批次查询行号、系统名称、失败阶段、失败原因；可扩展按错误码筛选。
4. 批次历史分页：按权限查询操作人、时间和状态。
5. 失败数据导出：经需求确认后提供，导出内容防止公式注入，受同等权限控制。

示例逻辑返回：

```json
{
  "batchId": "B001",
  "status": "PARTIAL_SUCCESS",
  "processedCount": 100,
  "successCount": 95,
  "failureCount": 5
}
```

- 技术请求成功与所有行成功分开表达，前端必须依据业务状态展示。
- 一行可包含多个字段错误，失败行数与错误条数不可混用。
- 接口分页查询，上传响应不携带无限错误列表。
- 重启、中断或文件损坏后的页面必须提示已提交记录不会自动回滚。
- 生产环境必须校验批次归属和查看权限，防止通过猜测批次号读取他人数据。

## 9. 性能与资源优化

### 9.1 首期可采用的轻量方案

在确认同步逐行方案后：

- EasyExcel 逐行处理，不积累整份待插入实体。
- 小型字典按本次导入加载；单位按需查询并缓存解析结果。
- 缓存无匹配及歧义结果，避免错误输入反复查询，但参考数据变化策略按 C10 确认。
- 每行独立事务；批次汇总定期更新，结束时与持久化结果核对。
- 对查询和错误存储设置资源上限。

逐行独立事务会增加提交次数，这是部分成功与隔离性的成本；不能同时承诺与大批量提交相同的吞吐。

### 9.2 进一步优化

- 有界分块读取并收集去重名称/单位，批量加载参考数据，再逐行事务写入。
- 大型 IN 参数分片；不默认加载整个组织表。
- 按查询模式评估系统有效名称、单位、字典及行结果索引，结合执行计划验证，避免重复索引。
- 不把按行 SQL 次数降为按块次数描述成算法复杂度整体 O(1)。
- 即便不保存所有行，去重集合、单位缓存及错误缓冲仍可能随不同键数量增长；设定边界而不是宣称严格常量内存。
- 未明确补偿语义前，不为提速改为分块共用写事务，以免一行错误影响整块。

## 10. 幂等、重试与中断恢复

### 10.1 请求幂等

- 使用调用方幂等键并绑定操作主体/租户范围，服务端核验内容摘要。
- 相同键相同内容返回已有批次及结果，相同键不同内容拒绝。
- 并发提交同一幂等键由数据库唯一约束等机制保障，不只先查询再创建。
- 文件摘要用于完整性和内容校验，不作为永久禁止重复上传的唯一规则。

### 10.2 行幂等与未知提交结果

- 同一批次同一来源行只能产生一个最终处理结果。
- 事务内检查/占用行标识与业务写入协调，避免恢复或重试重复插入。
- 网络断开、提交响应丢失时先核对持久化结果，不能直接判定行失败并再次执行。
- 新批次重导已成功的行仍遵守只新增，报已有名称，不改成覆盖。
- 修正失败行后的重导、自动重试及恢复是否复用批次属于不同语义，实施前明确，不混用。

## 11. 可观测性与安全边界

- 结构化日志包含批次号、请求标识、Excel 行号、阶段和稳定错误码。
- 指标区分解析、参考数据加载、校验、写入、审计和总耗时，以及成功率、错误类型、处理中批次数。
- 文件检查涵盖空文件、空文件名、大小写后缀、实际格式及损坏文件，不能只依赖扩展名。
- 设置上传大小、行数、单元格长度、解析时间/资源边界，关注压缩型文件的资源消耗。
- 不逐行打印完整敏感数据，不向前端透传底层异常。
- 失败报告导出防止单元格内容被解释为公式。
- 原项目适配时补全真实身份、权限及审计主体；最小项目不伪造已具备生产级认证。

## 12. 分阶段需求与验收

### 阶段 0：规则确认与数据设计

**需求**：确认 C01～C07 中影响首期的选项，梳理现有数据、表结构及接口契约，定义错误分类、行结果和批次状态。

**交付**：确认后的需求、逻辑/物理表设计、迁移及回退方案、接口草案。

**验收**：对重名、空文件、部分成功、未知提交和中断都能给出唯一且明确的处理规则；没有将待确认项当作已批准需求。

### 阶段 1：部分成功的完整闭环

**需求**：

- 拆分编排、行校验转换、行事务和审计职责；去掉吞异常。
- 新增批次和行结果存储，实现失败行入表及分页查询。
- 合法行独立事务插入，失败行不影响后续合法行，保留只新增规则。
- 严格校验必填、长度、字典、单位唯一匹配，修正行号，明确文件级错误处理。
- 确认并落实名称规则与数据库有效名称唯一约束。
- 成功行证据与业务原子提交，可核对最终统计。
- 提供上传结果与批次详情，采用已确认的同步/异步方式。
- 最低限度资源限制和安全错误输出不可推迟。

**验收场景**：

1. 文件 10 行，8 行合法、2 行普通错误：8 条业务新增、2 条失败结果，数量与状态一致。
2. 中间一行插入冲突，前后合法行均可成功，失败原因对应实际 Excel 行。
3. 所有行均失败、仅表头、错误表头有明确不同结果。
4. 库内同名不覆盖，批内同名按已确认规则执行。
5. 并发同名只产生一条有效系统记录。
6. 单位/字典无匹配和多匹配均不写错关联。
7. 审计保存失败时不会返回普通完成；中断状态不掩盖已经提交的行。

### 阶段 2：查询与吞吐优化

**需求**：单次导入参考数据缓存、有界分块预加载、SQL 与索引优化、减少重复查询和批次更新、阶段耗时指标。

**验收**：同一测试数据集比较查询次数、耗时、内存及事务提交成本；保持阶段 1 的逐行隔离、准确性和审计结果不变；性能目标在有环境和基线后确定，不预先承诺倍数。

### 阶段 3：完整审计、权限与安全重试

**需求**：幂等协议、行级恢复核对、批次历史、原文件策略、失败数据导出、真实用户适配、权限及保留/清理策略。

**验收**：同键并发不重复执行；提交响应丢失可核对；跨用户越权查询被拒绝；失败记录、来源输入与业务主键可追溯；清理与导出符合权限和隐私规则。

阶段 1 的基本行证据和一致性不能以“阶段 3 再审计”为由省略，阶段 3 是增强而非补救基础正确性。

### 阶段 4：大文件与异步演进

**启用条件**：实际文件规模或同步超时证明确有必要；若 C02 选择首期异步，则最小任务可靠性能力前置到阶段 1。

**需求**：任务受理与状态管理、受控执行器/队列、进度查询、重启恢复、租约/心跳及重复执行防护；必要时使用暂存表，不默认引入消息中间件。

**验收**：重复调度不重复写入，任务重启后状态可恢复或明确中断，进度来自可核对数据，资源有界；致命错误停止后续处理但不抹去已成功结果。
